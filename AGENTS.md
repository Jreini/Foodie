# Foodie — Agent Guide

Foodie is a SwiftUI iPhone app that treats food as social media: discover restaurants, review them, keep a "Tasting List" of places to try, see what friends are eating, and let the app decide where to go. It is iPhone-only by product decision (no Android, no iPad investment).

### Building — don't

**Do not run builds yourself.** Justin builds and verifies every change in Xcode himself. Make the code change, say what needs verifying, and stop — don't run `xcodebuild`, don't launch the simulator, don't ask to build. He'll report back if something fails.

### Destroying data — don't

**There are real people using this app, and their reviews are in the database.** Test users are actively writing content. There is exactly one Supabase project — its URL is hard-coded in `SupabaseService.swift` — so **production is also the development environment**. There is no staging database to rehearse against, and no undo.

**Never write anything that removes user data.** That means no `drop table`, no `drop column`, no `delete from`, no `truncate`, no `drop schema` — not in a migration, not in a snippet suggested for the SQL editor, not "just to reset while testing".

Changes that destroy data without saying so also count:

- **Renaming or retyping a populated column.** `avatar_url` → `avatar_path` was safe only because nothing had ever written to it, and the migration says so out loud. Assume any other column has rows behind it.
- **Adding `not null` without a default and a backfill**, which fails the migration or silently requires clearing rows to apply.
- **Tightening a `check` constraint** that existing rows already violate.
- **Dropping and recreating a table** to change it — recreating is not editing.

**Migrations are additive.** Add the new column, backfill it, switch the app over, and leave the old one in place. A dead column costs nothing; a dropped one costs somebody their reviews.

**`20260802001200_remove_seed_restaurants.sql` is not a precedent.** It deleted rows, and it was fine, because it ran before there were real users and it removed seeded restaurants nobody had created. That window is closed.

**Don't run `delete_current_user()` against a real account.** It cascades through every user-owned table and there is no recovery. Throwaway accounts only — the Phase 7 doc says the same thing and means it more now.

**Don't clear the Storage buckets.** `review-photos` and `avatars` hold user content. Postgres refuses a direct `delete from storage.objects` anyway, so the only way to do it is deliberate client-side code — which is a good sign you shouldn't be.

**If something genuinely needs removing, stop and ask.** Propose the migration, say exactly what it destroys and roughly how many rows, and let Justin decide. Don't fold a destructive step into a larger change and mention it in passing.

**Take a backup before applying any migration.** `Tools/backup_db.sh` writes a verified local dump in seconds — see `docs/BACKUPS.md`, which also records what the Supabase plan itself retains and what a dump doesn't cover (the Storage buckets, chiefly). The rules above are there so a restore is never needed; the dump is there for when one is.

## Architecture

### Auth

`Foodie/Services/AuthManager.swift` is the single source of truth for the session. It is `@MainActor @Observable`, injected into the environment from `FoodieApp`, and read with `@Environment(AuthManager.self)`.

- It exposes one `state` that `RootView` switches on: `.loading` / `.signedOut` / `.needsUsername` / `.ready(user, profile)` / `.profileUnavailable`. `.loading` exists so the login screen never flashes while the SDK restores a keychain session; `.profileUnavailable` keeps a network blip from dumping a signed-in user back to login.
- Only `.ready` reaches the app proper, so anything under `MainTabView` can assume both a session and a complete profile.
- `AuthenticatedUser` is our own struct, not the SDK's `User`. That keeps Supabase types out of the views and avoids colliding with the app's own `User` model.
- Both sign-ins are **native** token flows (no web view): Apple via `SignInWithAppleButton` → `signInWithIdToken`, Google via `GIDSignIn` → `signInWithIdToken`.
- **Apple returns the user's name only on the very first authorization**, so `AuthManager` writes it to Supabase user metadata immediately. Losing it means the user must revoke the app under Settings > Apple Account to get it back. Google returns it every time.
- Google's redirect comes back through the app's URL scheme, so `FoodieApp` must keep `.onOpenURL { GIDSignIn.sharedInstance.handle($0) }`. Sign-in silently never completes without it.
- Session persistence and token refresh are the SDK's job — don't hand-roll them.

### Places (MapKit)

`PlaceSearchService` wraps `MKLocalSearch`; `LocationProvider` is a one-shot `CLLocationManager` wrapper. Both are free with the developer account — no API key, no billing, no quota.

- **MapKit reports no price, hours, photos, or ratings.** Those fields on `Restaurant` are optional and stay nil rather than being defaulted to plausible-looking values. Don't "fix" a nil price by defaulting it to `1` — the UI hides unknown fields on purpose.
- **A place is persisted only when someone interacts with it** (review, like, tasting list). Browsing writes nothing, which is what keeps the table small. `ensureRestaurantPersisted` is the single entry point, and every write path calls it first.
- **The database owns identity, not the client.** The upsert conflicts on `mapkit_place_id`, so concurrent taps on the same restaurant converge on one row. The client-side UUID is derived deterministically from the place id (`PlaceSearchService.derivedId`) purely so SwiftUI has a stable handle before a row exists.
- `baselineTier` for a new place is a coarse guess from the POI category (MapKit has no fast-food category). That's what `baseline_tier` is for — the first real placement starts correcting it.

### Photos and Storage

`PhotoUploadService` handles both buckets: review photos in `review-photos`, avatars in `avatars`.

- **Always downscale before upload** (review photos 1600px long edge at JPEG 0.8; avatars 512px at 0.85, since nothing shows one bigger than ~80pt). Egress is the quota this app would outgrow first, and every view counts again — uploading originals would burn it fast.
- **A new avatar is cropped before it is uploaded.** `AvatarCropView` presents the photo inside the same circle the app draws avatars in, with pan and pinch, and bakes the result in — so the person choosing the picture decides what it shows, rather than `scaledToFill` centre-cropping it at display time and cutting someone out. The crop is a *square*: JPEG has no alpha and every avatar is already clipped to a `Circle()`, so baking the circle in would only add a black box on the first screen that forgot to.
- **Avatars live in their own bucket, not a folder inside `review-photos`.** That keeps "clear my review photos" and "replace my avatar" from ever reaching each other's files. `profiles.avatar_path` stores the object path, not a URL — the CDN host is not part of the identity.
- **Every avatar upload gets a fresh UUID filename**, which is what makes the one-year cache header safe: a replacement is a new path, so nothing needs invalidating. The old file is deleted only after the profile row stops pointing at it. Reusing a path would make an upload look like it silently failed.
- **Paths must be `<user_id>/<uuid>.jpg`, lowercased.** The bucket's INSERT policy checks the first path segment against `auth.uid()`, so the shape is load-bearing. **Swift's `UUID.uuidString` is uppercase and Postgres's `uuid::text` is lowercase** — comparing them unmodified fails every time. Lowercase any UUID that crosses into a SQL string comparison.
- Both buckets are **public-read** so images load from the CDN without a signed-URL round trip. Writes are still per-user. Avatars are public on purpose beyond convenience: non-friends need to recognise someone who turns up in a username search.
- Upload the image *before* writing the row that references it — a review or profile pointing at a failed upload renders as broken permanently.
- **Never `delete from storage.objects` in SQL.** Postgres blocks it (42501, "Use the Storage API instead") to avoid orphaning the underlying files. Deletion has to go through the Storage API from an authenticated client — which is why account deletion clears both folders client-side *before* removing the user.
- **The camera needs `NSCameraUsageDescription`** in `Foodie/Info.plist` or the app is killed the moment `CameraPicker` appears. `PhotosPicker` needs no permission string at all — it runs out of process — which is why only the camera path has one.

### Database

Schema lives in `supabase/migrations/`, applied in filename order. Ten tables and two storage buckets; see `docs/PHASE2_SETUP.md` for how to apply and verify them.

- **RLS is the only security boundary.** The publishable key ships in the app, so a missing or wrong policy *is* a data leak. Every policy is scoped `to authenticated` and wraps `auth.uid()` as `(select auth.uid())` so the planner evaluates it once per query rather than once per row.
- **Absent policies are deliberate.** `restaurants` has no UPDATE policy and `activities` has no INSERT policy — only `SECURITY DEFINER` triggers should write there. Adding a client-facing policy to either would let anyone forge ratings or fake a friend's activity.
- **Any insert that asks for its row back needs a SELECT policy that passes immediately.** PostgREST sends `Prefer: return=representation`, so inserts are `INSERT ... RETURNING` and Postgres applies the SELECT policy to the returned row. A SELECT policy that depends on a row created by an AFTER INSERT trigger will fail, because AFTER triggers fire after RETURNING is evaluated — that's what broke list creation and why migration `...000800` lets owners see their lists directly rather than only through membership.
- **`is_friend()` / `is_list_member()` / `is_list_owner()` are `SECURITY DEFINER` on purpose.** They bypass RLS to break policy recursion (a `list_members` policy querying `list_members` would loop forever). All set `search_path = ''`; keep it that way.
- **`group_pick_candidates()` is `SECURITY INVOKER`, also on purpose** — the opposite call. It runs as the caller *so that* RLS applies: the `likes`/`tasting_list` policies already limit rows to the caller and their accepted friends, so a stranger's id contributes nothing. Making it DEFINER would turn it into a way to read anyone's saved restaurants.
- **`friend_count()` is DEFINER because the friendships policy hides other people's edges** — counting a friend's friends client-side always returns 1. It returns a single integer and never *who*, which is the line: anything richer belongs behind a friendship check. Note it's `revoke`d from `PUBLIC` before being granted to `authenticated`, since functions are executable by everyone by default and RPCs are reachable without a session.
- Server-side logic is all in Postgres — profile creation on signup, restaurant aggregate recompute, and activity feed rows are triggers, not app code. There is no application server.
- Tiers are `double precision` on [0,1], never enums.

### Data

MVVM with a protocol-seam data layer, designed so the mock backend can be swapped for a real one:

```
Views (SwiftUI)  →  ViewModels (@Observable)  →  DataServiceProtocol  →  MockDataService
```

- `Foodie/Services/DataServiceProtocol.swift` — the single `async throws` contract for all data operations, plus `DataServices.current`, which resolves to `SupabaseDataService` normally and `MockDataService` inside SwiftUI previews (detected via `XCODE_RUNNING_FOR_PREVIEWS`). View models default to `DataServices.current`, so previews never hit the network — they'd have no session anyway.
- `Foodie/Services/SupabaseDataService.swift` — the live implementation. Row DTOs are private to that file and deliberately separate from the app models, because the DB shape and the UI shape differ on purpose (`Restaurant.imageName` is a UI placeholder with no column; `Review.text` maps to the `body` column).
- `Foodie/Services/MockDataService.swift` — hard-coded sample data with stable UUIDs. **Keep it conforming.** Its `async throws` methods never actually suspend or throw; matching the signature is the whole point.
- **Don't add client-side filters believing they're security.** `fetchActivityFeed` selects the whole table on purpose — RLS narrows it to the caller and their friends server-side.
- **`User.friendIds` is only meaningful for the signed-in user.** Everyone else arrives with it empty, because the friendships policy hides their edges — so `user.friendCount` reads 0 for a friend and is not a bug to "fix" client-side. `friendCount(for:)` is the way to get someone else's, and it counts server-side.
- **A screen that shows less to a stranger is not enforcing anything.** RLS already returns nothing; the client only predicts that, so the UI can say "friends only" instead of rendering a misleading empty list. Never invert this — a client-side check is a display decision, never a boundary.
- View models are `@MainActor @Observable` with `isLoading` / `errorMessage`. Views load with `.task` (not `.onAppear`) and offer `.refreshable`. Writes are optimistic: flip local state, sync, roll back on failure.
- **Realtime is used in exactly one place** — `listEntriesChanged(listId:)`, driving the open shared list. Everything else is happy with pull-to-refresh, and a socket per screen would be waste. It goes through the protocol (mock returns a stream that never fires) so previews need no connection.
- **Realtime honours RLS**, so a non-member receives nothing at all. On any change the view model refetches rather than patching from the payload: one query handles insert/update/delete identically and can't drift.

### Notifications

A trigger writes a row into `notifications`, a Database Webhook on that INSERT calls the `push` Edge Function, and the function delivers it to the recipient's devices through APNs. See `docs/PHASE9_SETUP.md` for the console setup and the troubleshooting list.

- **`supabase/functions/push/index.ts` has no imports, deliberately.** The npm `apn` package cannot run in Supabase's Deno runtime — it reaches for `node:tls`. Web Crypto signs the ES256 token and `fetch` negotiates HTTP/2 with APNs by itself, so there is nothing to keep current. **Don't add a push library.**
- **Push is a tap on the shoulder, not the delivery mechanism.** The `notifications` row is the authoritative copy and also backs the in-app inbox, because iOS asks for the permission exactly once and plenty of people decline.
- **Only triggers write `notifications`** — no INSERT policy, same reasoning as `activities`. `authenticated` holds an UPDATE grant on `read_at` alone (`revoke update` then `grant update (read_at)`), because RLS chooses rows and has nothing to say about columns.
- **`device_tokens` is keyed by the token, not the user.** A token identifies a device+install, so a second account signing in on the same phone must *move* the row — two rows would send one user's notifications to another's phone. `register_device_token()` is `SECURITY DEFINER` precisely so it can take a row from its previous owner; it always writes `auth.uid()`, so nobody can register a token to someone else.
- **There is no SELECT policy on `device_tokens`.** The client only writes its own; the Edge Function reads them with the service key.
- **`is_sandbox` is a `#if DEBUG` guess, and the server corrects it.** Debug builds get sandbox tokens and TestFlight gets production ones, but a Release build run from Xcode breaks that rule. On `BadDeviceToken` the function retries the other APNs host and rewrites the flag, which turns a silent, baffling failure into a self-healing one.
- **Navigation goes through `PushRouter`** (`Services/PushRouter.swift`), not direct pushes: a tapped push and a tapped inbox row must land identically, and the destination may live in a different tab. Screens *pull* a pending destination — `consume(_:)` claims only what they can show — so a notification tapped at cold launch still works when its tab doesn't exist yet. Both `onAppear` and `onChange` are needed; neither alone covers both cold launch and a running app.
- `AppDelegate` in `FoodieApp.swift` exists for one callback only: APNs hands over the device token through UIKit, and SwiftUI has no equivalent.

### Directory map (`Foodie/`)

- `FoodieApp.swift` — app entry; injects `AuthManager` and `PushRouter` into the environment (and a Core Data context no feature uses). Also holds the `AppDelegate` that receives the APNs token.
- `Views/RootView.swift` — switches on `AuthManager.state`; only `.ready` reaches `MainTabView`.
- `Models/` — plain structs: `User`, `Profile`, `Friendship` (+ `FriendshipState`), `Restaurant`, `Review`, `TastingListEntry`, `SharedList`, `FriendActivity`, `AppNotification`, `RestaurantTier`. (`AppNotification`, not `Notification` — Foundation owns that name.)
- `ViewModels/` — one per screen: `FeedViewModel`, `DiscoverViewModel`, `DecisionEngineViewModel`, `TastingListViewModel`, `ProfileViewModel`, `UserProfileViewModel`, `FriendsViewModel`, `SharedListsViewModel`, `SharedListDetailViewModel`, `NotificationsViewModel`.
- `Views/` — grouped by feature: `Auth/`, `Feed/`, `Discover/`, `Decide/`, `Lists/`, `Map/`, `Friends/`, `Notifications/`, `Profile/`, plus shared `Components/` (star ratings, tier badges/slider, chips, rows, `ProfileImageView`, `CameraPicker`, `FullScreenImageView`).
- `Views/MainTabView.swift` — five tabs: Feed, Discover, Map, Decide, Profile. Each tab owns one `NavigationStack`, and its root registers every destination reachable below it.
- `Views/Profile/ProfileComponents.swift` — the pieces your profile and somebody else's both use (`ProfileStat`, `ProfileReviewCard`, `ProfileSegmentPlaceholder`), so the two screens can't drift apart.
- `Services/` — `DataServiceProtocol` + its two implementations, `AuthManager`, `ProfileService`, `SupabaseService`, `PhotoUploadService`, `PlaceSearchService`, `LocationProvider`, `TierFlaggingService`, `PushNotificationService`, `PushRouter`.
- `Theme/AppTheme.swift` — all design tokens (colors, spacing, radii, card style). **Always use `AppTheme` tokens instead of hard-coded values**; primary accent is a warm orange/coral.

## The tier system (the app's signature concept)

Restaurants live on a continuous 0.0 → 1.0 spectrum (`RestaurantTier`) from Fast Food to Fine Dining, with five named zones (Fast Food, Fast-Casual, Casual Dining, Upscale Casual, Fine Dining) that deliberately overlap at boundaries.

- A star rating is interpreted *within* a tier: 5-star fast food ≠ 5-star fine dining. Every `Review` carries a `tierPlacement`.
- `Restaurant` stores both a `baselineTier` (seed) and `averageTier` (crowd-adjusted, stored rather than computed so list rows don't re-aggregate).
- `TierFlaggingService` detects outlier placements (e.g. McDonald's placed in Fine Dining) and tells the UI to ask the user to confirm. Placement must be ≥ 0.25 away *and* ≥ 2 named zones apart, with at least 1 existing review, before it flags.

Preserve this model in any backend schema: tiers are `Double`s in [0,1], not enums.

## Feature notes

- **Feed** — paginated friend activity cards (reviewed / checked in / added to tasting list / liked), plus the Friends button in the toolbar, dotted red when a request is waiting. Each card carries two sibling links: the top row to the person, the rest to the restaurant.
- **Discover** — searchable, cuisine-filterable restaurant list with detail views and reviews. Reviewer names on a restaurant page link to their profile.
- **Map** — real, not a placeholder (`NearbyMapView`): MapKit results near the user, pins colored by tier zone, re-searchable after panning.
- **Decide** — the decision engine: "Roll the Dice" (random for you, or a real group pick aggregating friends' overlapping likes and tasting lists via `group_pick_candidates`), "Discover a New Taste", the tasting list, and shared lists.
- **Tasting List** — per-user want-to-try list with notes; add/remove/random-pick.
- **Shared Lists** — lists several people build together, kept live with the app's only Realtime subscription.
- **Friends** — username search, request/accept/decline, unfriend. Reached from the Feed toolbar and the friend count on Profile. Rows for people you already have an edge with open their profile; search results deliberately don't, because there the row *is* the Add button.
- **Profile** — user info with Reviews / Liked / Tasting List segments, editable name, bio and picture. `UserProfileView` is the same screen for somebody else, reached by tapping a person anywhere they appear — the friends list, a feed card, a review. It also carries the Add Friend / Accept / Friends▾ control, so the profile is where the relationship is managed too.

  What it may show depends on the friendship, and the *database* decides that: reviews are readable by any signed-in user, but `likes` and `tasting_list` return rows only to the owner and their accepted friends. `canSeeSavedRestaurants` is the client predicting that, so those sections say "friends only" rather than looking empty, and the tasting-list stat shows `—` rather than `0`.

## Conventions

- Comments are plain `//` sentence-style explaining *why* (see existing models); match that density — the codebase is deliberately well-commented.
- Views stay dumb; filtering/aggregation logic belongs in view models or services.
- Mood tags are free-form strings; price level is 1–4 (`$`–`$$$$`), nil when unknown.
- **Don't derive a value from a tap's coordinates inside a Form or List.** The row is wider than its content, so the leading offset makes the arithmetic wrong — that's what made every star tap read as 5. Use per-element buttons with `contentShape`.
- **Navigate by value, never by `NavigationLink { SomeView() }`.** A view-based link re-activates itself when the path changes underneath it, so it pushes its destination a second time on top of whatever you just opened — that's what put the friends list back over a friend's profile. It only bites once *something* in the stack pushes a value, which is why the app got away with it until profiles were linkable. One view-based link left in a chain is enough to bring it back.
- **`navigationDestination(for:)` goes at the root of a stack, once per type.** SwiftUI keeps one destination per type per `NavigationStack`; declaring the same type again deeper makes which one wins depend on where the user is standing. Each tab's root registers everything reachable below it — `personProfileDestination()` and `friendsListDestination()` are the shared ones — so screens push values without knowing what renders them.
- **A card that links to two places holds two sibling links, not a nested one.** A `NavigationLink` inside another does not work — that's why the feed card owns its own links instead of `FeedView` wrapping it. Give each label a `contentShape(Rectangle())` so the gaps are tappable too.
- **A `TextEditor` needs an explicit keyboard dismissal** (`@FocusState` plus a `.keyboard` toolbar item). Return inserts a newline, so there's no other way out.
- **Render a person through `ProfileImageView`**, which takes a `User` or a raw avatar path and handles the missing-picture fallback. Don't build an avatar inline — half the app would keep the placeholder forever.
- **A photo opens full screen through `FullScreenImageView`**, presented with `.fullScreenCover(item:)` from an `ImageViewerSource`. A photo is a detour, not a destination: pushing it would put a Back button on it and leave it in the navigation stack. Hand the viewer the whole set (a review's photos, say) with the index that was tapped, so it can page rather than being reopened per photo.
- **Most avatars must keep their tap.** `ProfileImageView` only opens full screen when asked (`opensFullScreen: true`), because nearly every avatar in the app sits inside a `NavigationLink` where the tap means "open this person". Only the header avatars on `ProfileView` and `UserProfileView`, which link nowhere, take it — and only when there's a real picture, since a full-screen SF Symbol placeholder is a dead end.
- **A centred row of self-sized columns isn't centred.** The profile stats looked crooked because "Tasting List" is half again as wide as "Reviews", so each number sat in the middle of its own label rather than its own third. Give columns `frame(maxWidth: .infinity)` when the *contents* need to line up, not just the row.
